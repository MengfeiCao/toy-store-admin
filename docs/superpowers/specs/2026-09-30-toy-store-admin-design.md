# 玩具销售后台 MVP 设计规格

## 1 背景与目标

本系统供一家玩具店的店主和店员内部使用。销售订单来自线下门店或微信接单，由员工在后台手工录入，不连接淘宝、拼多多、抖音等电商平台。

第一版的目标是建立一条可以实际操作、数据可追溯的经营闭环：

```text
维护玩具 → 确认入库 → 查看库存 → 创建销售订单 → 确认出库 → 标记收款 → 查看销售与利润
```

系统完成的判断标准不是页面数量，而是使用一组固定业务数据完成整条流程后，订单金额、当前库存、库存流水、销售额、成本和毛利润均与人工计算一致；重复提交、库存不足和越权操作不会破坏数据。

## 2 设计原则与业务假设

- 第一版服务单个企业、单个仓库和单一币种。
- 每一种需要独立计算库存的颜色或款式建立为独立玩具商品。
- 玩具数量使用大于零的整数，不处理散装或小数数量。
- 商品售价在订单中固定使用，店员不能修改，也没有优惠金额。
- 收款只有未收款和已收款，不支持部分收款。
- 订单确认时不预占库存，实际出库时再次校验并扣减库存。
- 第一版整单出库；任意商品库存不足时，整张订单出库失败。
- 已完成订单保存名称、货号、售价和成本快照，商品资料的后续修改不影响历史数据。
- 商品成本采用出库时玩具资料中的当前成本价，不计算移动平均成本、运费、税费或其他经营费用。

## 3 MVP 范围

### 3.1 第一版包含

1. 登录、退出和账号状态检查。
2. 店主和店员两个角色。
3. 玩具资料维护、图片、在售和停用状态。
4. 入库单、入库确认、当前库存和库存流水。
5. 客户资料，以及无需建档的散客销售。
6. 销售订单、固定售价、订单确认和整单出库。
7. 未收款和已收款两种状态，以及收款方式和时间。
8. 店主经营首页与店员工作首页。
9. 低库存提醒、基础筛选和列表查询。

### 3.2 第一版不包含

- 电商平台订单同步。
- 会员积分、优惠券、折扣和复杂促销。
- 部分收款、预收款、退款和收款明细台账。
- 退货、换货、库存冲销和盘点调整。
- 供应商、采购结算和采购审批。
- 多门店、多仓库和多币种。
- 会计凭证、发票和完整财务系统。
- 打印小票、扫码枪集成、短信和微信通知。
- 复杂部门权限和按人员隔离的数据权限。

## 4 角色与权限

### 4.1 店主

店主可以访问全部业务页面，查看和修改成本价，查看销售额、商品成本和毛利润，管理用户账号，停用玩具，并撤销错误的收款状态。

### 4.2 店员

店员可以查看在售玩具、售价和库存，处理入库、客户、销售订单、出库和收款。店员不能查看成本价、商品成本和毛利润，不能管理用户、停用玩具或撤销收款。

成本价是创建商品时的必填字段，又必须对店员保密，因此商品创建由店主完成。店员可以修改名称、图片、分类、品牌、适合年龄、条码和低库存值等非敏感字段，不能创建商品，也不能修改货号、售价、成本价或商品状态。此规则消除了“店员创建商品但不能看到必填成本价”的权限冲突。

### 4.3 关键操作记录

入库确认、订单创建、订单确认、出库、标记收款及撤销收款均保存操作人和操作时间。第一版不建立独立的审计日志页面。

## 5 业务流程与状态

### 5.1 入库流程

```text
创建入库草稿 → 添加玩具和数量 → 确认入库 → 增加库存 → 生成库存流水
```

入库单状态为 `draft` 和 `posted`。草稿可以编辑或删除；已入库单据不可修改或删除。确认入库必须在同一个数据库事务中完成状态检查、库存增加和流水写入。

### 5.2 销售订单流程

```text
创建订单 → 选择客户或散客 → 添加玩具和数量 → 自动带出售价
→ 保存草稿 → 确认订单 → 确认出库 → 标记已收款
```

订单状态为：

- `draft`：可以修改客户、玩具和数量，也可以删除。
- `pending_shipment`：已经确认，明细锁定，可以执行出库或取消。
- `completed`：已经整单出库，不可修改或取消。
- `cancelled`：出库前取消，仅保留记录。

确认订单不扣减或预占库存。确认出库时重新检查全部商品库存；库存充足则在一个事务中扣减库存、保存成本快照、写入负向库存流水并将订单变为已完成。库存不足时全部操作回滚。

### 5.3 收款流程

收款状态为 `unpaid` 和 `paid`。只有已完成订单可以标记为已收款。标记时保存收款方式、收款时间和操作人。收款方式为微信、支付宝、现金和其他。

已收款操作不能重复执行。店主可以将错误的已收款状态撤销为未收款，撤销时保存操作人和时间。第一版不生成独立收款记录，也不支持部分金额。

### 5.4 金额规则

```text
商品行金额 = 数量 × 售价快照
订单总额 = 所有商品行金额之和
商品成本 = 所有商品行的数量 × 成本快照之和
毛利润 = 订单总额 - 商品成本
```

订单总额由服务端或数据库根据明细重新计算，前端提交的总额不作为可信结果。

## 6 页面与交互设计

系统采用桌面优先的左侧固定导航。复杂订单使用完整页面，简单资料编辑使用抽屉或对话框。

### 6.1 页面清单

| 菜单 | 页面 | 主要功能 |
|---|---|---|
| 首页 | 经营概览 | 今日及本月订单和销售数据、低库存提醒；利润数据仅店主可见 |
| 玩具管理 | 玩具列表 | 查询、查看、新增、编辑、停用和查看当前库存 |
| 库存管理 | 入库单 | 新建入库单、维护明细和确认入库 |
| 库存管理 | 库存流水 | 按玩具、日期和来源查询库存变化 |
| 客户管理 | 客户列表 | 新增和编辑客户，查看关联订单 |
| 销售管理 | 销售订单 | 创建、确认、出库、取消、标记收款和查询历史订单 |
| 系统管理 | 用户管理 | 店主管理店员账号、角色和账号状态 |

登录页不出现在左侧导航中。

### 6.2 玩具字段

玩具包含名称、唯一货号、可选条码、分类、可选品牌、可选适合年龄、成本价、售价、当前库存、可选低库存值、可选主图和状态。当前库存由业务事务维护，任何页面均不能直接编辑。

### 6.3 订单交互

订单选择玩具后自动显示当前售价，价格输入框只读。数量变化时前端实时展示行金额和总额，保存时服务端重新计算。订单列表支持按订单号、客户、订单状态、收款状态和日期筛选。

店主首页展示销售额、商品成本、毛利润、订单数和库存不足；店员首页不返回或显示成本及利润数据，只展示销售额、订单数、待出库订单和库存不足。

## 7 技术架构

### 7.1 技术选择

- 前端：React、TypeScript、Vite。
- 界面组件：Ant Design。
- 登录：Supabase Auth。
- 数据库：Supabase PostgreSQL。
- 图片存储：Supabase Storage。
- 前端部署：Vercel。

第一版不建设独立 Node.js 后端。普通查询和资料维护通过 Supabase 数据接口完成；确认入库、订单出库和标记或撤销收款通过受保护的 PostgreSQL 函数完成。

### 7.2 组件边界

1. 页面层负责列表、表单、状态提示和用户交互。
2. 前端业务层负责输入校验、界面权限和调用封装，不直接决定库存结果。
3. 数据库函数负责关键状态校验、金额计算、并发控制和原子事务。
4. PostgreSQL 保存业务数据，Supabase Auth 保存登录身份，Storage 保存商品图片。

数据库启用行级安全策略。浏览器只持有公开客户端配置，不包含服务端密钥。成本和利润的保密不能只依赖隐藏前端字段，店员使用的查询本身不得返回这些数据。

## 8 数据模型

第一版使用 8 张业务表，不单独建立分类、仓库、支付或财务表。

### 8.1 users 用户资料

- `id uuid`：主键，同时关联 Supabase Auth 用户。
- `name text`：姓名。
- `role text`：`owner` 或 `staff`。
- `status text`：`active` 或 `disabled`。
- `created_at timestamptz`。

### 8.2 products 玩具

- `id uuid`、`sku text unique`、`barcode text`、`name text`。
- `category text`、`brand text`、`age_range text`、`image_path text`。
- `cost_price numeric(12,2)`、`sale_price numeric(12,2)`。
- `stock_qty integer`、`low_stock_threshold integer`。
- `status text`：`active` 或 `inactive`。
- `created_at`、`updated_at`。

货号唯一，价格与库存非负。新商品库存为零，只能通过确认入库和销售出库改变。

### 8.3 customers 客户

- `id uuid`、`name text`、`phone text`、`address text`、`remark text`。
- `created_at`、`updated_at`。

销售订单的客户可以为空，空值表示散客。已关联订单的客户不能删除。

### 8.4 stock_in_orders 入库单

- `id uuid`、`order_no text unique`、`status text`、`remark text`。
- `created_by uuid`、`created_at`、`posted_by uuid`、`posted_at`。

### 8.5 stock_in_items 入库明细

- `id uuid`、`stock_in_order_id uuid`、`product_id uuid`、`quantity integer`。

数量大于零，同一入库单中的相同玩具合并为一行。

### 8.6 sales_orders 销售订单

- `id uuid`、`order_no text unique`、`customer_id uuid nullable`。
- `status text`、`total_amount numeric(12,2)`、`remark text`。
- `payment_status text`、`payment_method text nullable`、`paid_at timestamptz nullable`、`paid_by uuid nullable`。
- `payment_reverted_at timestamptz nullable`、`payment_reverted_by uuid nullable`。
- `created_by`、`created_at`、`confirmed_by`、`confirmed_at`、`shipped_by`、`shipped_at`。

### 8.7 sales_order_items 销售明细

- `id uuid`、`sales_order_id uuid`、`product_id uuid`、`quantity integer`。
- `product_name_snapshot text`、`sku_snapshot text`。
- `unit_price numeric(12,2)`、`unit_cost_snapshot numeric(12,2) nullable`。

售价在加入订单时从商品资料复制并锁定；成本在出库时复制。数量大于零，同一订单中的相同玩具合并为一行。

### 8.8 stock_records 库存流水

- `id uuid`、`product_id uuid`、`quantity_delta integer`。
- `stock_in_item_id uuid nullable`、`sales_order_item_id uuid nullable`。
- `created_by uuid`、`created_at timestamptz`。

入库为正、销售出库为负。两个来源字段有且仅有一个非空，并分别设置唯一约束，确保一条业务明细只生成一次流水。

## 9 关键事务与并发控制

### 9.1 确认入库

事务锁定入库单，验证状态仍为草稿，校验全部明细后增加商品库存、写入流水并更新单据状态。重复调用已入库单据不会再次增加库存。

### 9.2 确认出库

事务锁定订单及涉及的商品记录，验证订单为待出库并检查全部库存。校验通过后扣减库存、保存成本快照、写入每条负向流水并更新订单状态。并发争用最后库存时，后执行且库存不足的订单失败。

### 9.3 标记收款与撤销

标记收款函数只接受已完成且未收款的订单。撤销函数仅店主可调用，只接受已收款订单。两种操作均记录人员与时间，重复调用不会重复生效。

## 10 校验与错误处理

- 必填字段为空、货号重复、数量非正整数或价格为负时拒绝保存。
- 库存不足时返回具体缺货玩具和可用数量，事务不产生任何部分修改。
- 关键按钮提交后进入处理中状态，并在结果返回前禁止再次点击。
- 如果请求超时或网络中断，页面先重新查询单据状态，不直接重复执行关键操作。
- 登录过期后返回登录页；已经保存到数据库的草稿不丢失。
- 图片上传失败可以重试，不影响其他已经保存的商品资料。
- 页面向用户显示可执行的错误说明，系统日志保留技术错误和关联单据编号。
- 已产生业务记录的玩具只能停用；已确认入库单、已完成订单和库存流水不能直接修改或删除。

## 11 验收与测试

### 11.1 固定业务案例

使用玩具“恐龙积木”，成本价 60 元、售价 100 元、初始库存 0。确认入库 10 件，创建销售 3 件的订单，确认并出库，然后标记已收款。

预期结果：订单总额 300 元，出库后库存 7 件，商品成本 180 元，毛利润 120 元，收款状态为已收款。修改商品售价为 120 元后，历史订单仍保持 300 元。

### 11.2 权限案例

- 店员不能读取成本价、商品成本和毛利润。
- 店员不能管理用户、停用商品或撤销收款。
- 店主可以完成上述操作。
- 未登录和已禁用账号不能访问业务数据。

### 11.3 异常案例

- 重复确认入库或出库只生效一次。
- 库存 7 件时出库 8 件失败，库存、流水和订单状态均不改变。
- 两个订单并发争用不足库存时不出现负库存。
- 重复标记收款不能产生第二次状态变化。
- 已引用商品、已确认单据和流水不能被直接删除或篡改。

### 11.4 测试层次

1. 业务规则测试覆盖金额、状态、权限和输入校验。
2. 数据库集成测试覆盖事务、重复调用、库存不足和并发出库。
3. 页面端到端测试覆盖登录、商品、入库、订单、出库、收款和首页统计。

## 12 开发顺序与阶段出口

1. 建立数据库迁移、登录和角色权限；两类账号可以正确登录并获得不同数据。
2. 完成玩具管理；店主可以创建商品，店员不能读取成本。
3. 完成入库与库存流水；确认入库只生效一次，当前库存与流水合计一致。
4. 完成客户管理；订单可以选择客户或散客。
5. 完成销售订单；售价自动带出且不可修改，总额由服务端计算。
6. 完成订单确认与出库；库存不足、重复调用和并发操作受控。
7. 完成收款状态；标记和店主撤销均可追溯。
8. 完成角色化首页和低库存提醒。
9. 执行固定案例、权限案例和异常案例，全部通过后部署试运行。

开发以纵向业务闭环为单位，每个阶段同时完成页面、权限、数据库操作和测试，不采用先做完全部前端再统一开发数据逻辑的方式。

## 13 上线交付

上线需要提供可运行的前端、数据库迁移和函数、权限策略、环境变量示例、部署地址、店主账号交接方式、简短操作说明及验收记录。生产环境需启用数据库备份，并将测试数据与正式数据分开。

## 14 后续迭代方向

试运行后优先根据实际频率补充导出、扫码录入、盘点、退换货和库存调整。电商平台同步、供应商采购、多仓库、会员促销、打印和财务对接分别立项，不默认纳入第二版。
